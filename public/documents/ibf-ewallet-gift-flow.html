IGNATIUS BOOK FAIRS  ·  ENGINEERING SPEC DRAFT FOR MONDAY REVIEW

Gift-a-Wallet
grandparent → child eWallet funding

End-to-end flow, data model, and open questions for letting a parent send a tokenized link that lets a friend or family member fund a specific child's eWallet balance directly.

01 — CONTEXT

Where this fits into the existing system

Parents already buy store credit for their kids through three fixed BigCommerce products — $10, $25, $50 — and assign each purchase to a specific child. BigCommerce itself only exposes one flat store-credit field per customer account, so there's no native concept of "child A has $25, child B has $15." That per-child split is tracked entirely in our own ledger, which already works for the parent-driven purchase flow.

Rule of record: BigCommerce's store-credit field is always the pooled total. Our ledger database is the source of truth for how that total is divided across a parent's children.

This spec adds a new entry point into that same ledger — a tokenized link a parent can send to someone else (grandparent, family friend) that lets them fund the parent's kids directly, without ever touching the parent's login or card.

Two link shapes — one preferred. Every section below documents both a simple, single-child link (one link per kid) and a family & friends link (one link, every child, recipient chooses who to fund). The family & friends link is preferred — better UX for the recipient, one email instead of several. The single-child link is documented as a simpler fallback, not a firm launch decision either way.

03 — DATA MODEL

Schema additions

Two new tables layer on top of the existing parent / child / ledger structure. Nothing about the existing parent-purchase flow changes — a gift-link purchase writes to the same ledger table a normal purchase does, just via a different trigger.

04 — TOKEN CONTENTS

What the link actually carries

The token itself stays a short opaque string in the URL; it's a lookup key into gift_token, not a JWT carrying data client-side. On page load, the landing page resolves the token server-side and hydrates with the parent's full roster:

// resolved server-side from gift_token.token { "parent_id": "par_8841", // not shown to recipient "children": [ { "child_id": "chd_2290", "first_name": "Jimmy" }, { "child_id": "chd_2291", "first_name": "Susie" } ], "recipient_first_name": "Susan", "recipient_last_name": "Doyle", "recipient_email": "susan.doyle@example.com", "status": "pending", "expires_at": "2026-08-28T00:00:00Z" }

Recipient sees a pre-filled form (their name/email, editable) and a card for every child on the account — "Please support my children" — with an amount picker per kid. They set an amount for as many kids as they like, everything goes into one cart, and they check out once with their own payment method.

No separate schema for the single-child version. Same gift_token table, same payload shape — a single-child link is just this same children array with one entry instead of the full roster. The "Copy Emma's e-wallet share link" action (Section 06) generates a token whose resolved roster happens to contain only Emma.
05 — STOREFRONT LANDING PAGE

The "Special Gift Cart"

This is the storefront-side build: a modified, single-purpose variant of the existing cart + assignment + checkout flow, scoped only to gift-link sessions. Same underlying cart and checkout security already in place — the difference is what happens between "land on page" and "add to cart."

  • Entry: recipient arrives via the tokenized link, no login, no BigCommerce account required.
  • Roster render: page pulls the token's resolved children list and renders one card per child with its own amount picker (the three existing price points).
  • Modified assignment step: in the existing parent flow, the logged-in parent assigns each cart line to one of their own children. Here, the same assignment concept applies, but it's driven by the recipient picking amounts against the token's pre-resolved child list instead of a parent picking from their own account.
  • Cart: each child amount the recipient sets becomes its own line item, all under one cart tied to the token — not a generic storefront cart, a scoped one that only ever contains this parent's children and closes with the token.
  • Checkout: hands off to the existing, already-hardened checkout for payment. No changes needed there.
  • Likely implementation: custom storefront route wired through BigCommerce's Storefront GraphQL API, similar in shape to the existing catalog PDF generator work — not a native BigCommerce page template.
Real product pages, confirmed. The three price points are three separate BigCommerce products, each at its own URL — store.ignatiusbookfairs.com/e-wallet-10 / /e-wallet-25 / /e-wallet-50. That means the flow needs a step before the cart: a small picker page where the token resolves and the recipient chooses.

07 — LIFECYCLE & SECURITY

Token rules

  • Single-use. Once a token resolves to a completed order, status flips to used and the link can never charge again.
  • Expiring. Tokens carry an expires_at; past that, the landing page shows an expired state instead of checkout.
  • No parent credentials exposed. The recipient never sees parent account info beyond the child's first name — token resolves server-side.
  • n8n's role: listens for the BigCommerce order-completion webhook tied to a gift-link order, loops the cart's line items and writes one wallet_ledger credit row per child, updates the token status once the whole order is done, and triggers the parent notification email.
08 — DECISIONS

Resolved this pass, and what's deferred

  • Resolved
    Does one link cover one child, or the whole family?Both are documented, sharing one schema. Family & friends (whole roster, one link) is preferred for better recipient UX — one email instead of several. Single-child (one link per kid) is documented as the simpler fallback. Which one launches first isn't decided yet — see Section 06's scope-cutting note for what a single-child-only launch would look like.
  • Resolved
    Who picks the dollar amount — parent or recipient?Recipient picks per child at checkout time from the three existing products. Better UX for the person paying, and it's the same three price points regardless of how many kids they fund.
  • Resolved
    Does the parent's card get charged?No — the recipient pays directly. Only the resulting ledger credit is attributed to the parent's account / that child.
  • Resolved
    Can a link be reused or forwarded indefinitely?No — tokens are single-use and expire. A stale or already-used link shows an expired state.
  • Phase 2
    Can a parent reassign already-allocated credit between children after the fact?Not needed for v1. Flagged as a future enhancement to the ledger, not part of this build.
09 — EXISTING SYSTEM: QA FIELD NOTES

Manual testing findings — current e-wallet purchase flow

Testing on a live account against the existing (non-gift) e-wallet purchase flow surfaced four findings worth resolving before or alongside this build, since the gift flow leans on the same balance displays and the same product page.

1 — Order acceptance timing on first purchase

Purchased a $50 e-wallet by check for a test child. No balance showed anywhere (header, Account > Children, Parent Hub) until the order was manually marked done — then it appeared correctly in all three places. A second purchase ($25, same child) showed up immediately, before that check payment had been accepted.

Which is weird — why did it not show on first order immediately? Was this a timing issue, or the fact that the check was showing as pending?

2 — Header balance doesn't refresh live

Added a second child, bought a $10 e-wallet for them, checked out. After the order completed, the top-nav header balance chip still showed the old $75 total — Parent Hub and Account > Children were both already correct at $85, only the header lagged. A manual page refresh fixed it.

What is the exact trigger for updating the header balance? Can we push a refresh to prevent this UI inconsistency?

Relevant to this build: the gift flow's Step 0 → Step 1 redirect (Section 05) happens fast, right after checkout. If header balance relies on the same lagging trigger, a parent could see the same stale-balance moment right after a gift order completes, not just after their own purchases.

3 — Quantity selector on the e-wallet product pages

Decision: lock quantity to 1 on all three e-wallet PDPs. Buying qty 2 of a $25 e-wallet product is confusing next to just buying the $50 product — no reason to support it. Fix with JS on the three e-wallet product pages: hide the quantity stepper and force the hidden quantity input to 1, so "Add to Cart" can never submit anything else.

// illustrative — swap selectors for the real qty stepper/input markup on the Next.js PDP // runs only on the three e-wallet PDPs (match by product slug/SKU) const EWALLET_SLUGS = ['e-wallet-10', 'e-wallet-25', 'e-wallet-50']; if (EWALLET_SLUGS.some(slug => location.pathname.includes(slug))) { const qtyWrap = document.querySelector('[data-qty-selector]'); const qtyInput = document.querySelector('input[name="qty[]"]'); if (qtyWrap) qtyWrap.style.display = 'none'; if (qtyInput) { qtyInput.value = 1; qtyInput.setAttribute('readonly', 'true'); } }

Step 0's own add-to-cart mutation (Section 05) already hardcodes quantity to 1 regardless, so the gift picker was never affected — this is purely for the normal parent-purchase product page, where the selector is live today.

4 — Checkout offers unpurchased e-wallet balance as payment

Added $10 to cart, proceeded to checkout. Before that order had transacted at all, checkout showed a checkbox offering to pay using the $10 e-wallet balance — the same $10 this order was in the middle of purchasing, not yet-existing balance.

This is a real bug, not expected behavior: checkout should never offer a wallet balance that hasn't actually been purchased yet as a usable payment method.

Also confirmed clean

Parent Hub and Account > Children were accurate throughout every test; only the header chip showed the lag above. No need to separately accept a check payment for balances to eventually reflect correctly — the first non-update was a timing issue, not a check-payment-specific one.
